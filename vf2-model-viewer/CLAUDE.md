## 分かっていること

各項目の頭の札（dash.mjs はこの札で色分けする）: 【確定】本体のコードで確かめた　【数字】全ファイルで数を数えて確かめた
【絵】描いて見て確かめた　【推測】まだ確かめていない　【×】試して合わなかった

- 【数字】`.CMP` は CRICMP 2.10。展開は本体 0x1547c0/0x154e80 を写した（`cricmp.py`・`cricmp.js`）。102 ファイル全部で展開後の大きさが頭の値と一致、JS と Python の出力も一致
- 【数字】OBJ ファイル（展開後）＝ [モデル数] + モデル×N。モデル＝[番号] + 塊×4（各 [長さ][中身]）。全ファイルの最後のバイトまで区切れる
  - 塊3 が面の記録 40B: +0 頭、+4 法線、+0x10 頂点A、+0x1c 頂点B（float）
  - 頭 bit0-1 = 形（0 終わり・1 四角・2 三角）、bit8-9 = つなぎ方。手元の2点 P0,P1 で面 (P0,P1,B,A)。
    つなぎ方 0=描かずに P0=A,P1=B、2=P0=A,P1=B、1=P1=A、3=P0=B（本体 0x1c9cc0）
  - 並べた頂点の向きとファイルの法線: AKI1・PAI1・WOL2 で 99.2% 同じ向き、STAGE1 は全部同じ（数字で確認）
- 【絵】描いた部品は手（握り・開き・指違いが多数）・腕・脚・足・胴らしい形に見える（絵で確認。どれが何かは推測）

## 写し（PCSX2 のセーブステート）

- 【確定】.p2s は zip（中身は zstd、形式番号 93）。`python3 p2s.py disc/states/x.p2s` で eeMemory.bin（主メモリ 32MB）・GS.bin・Screenshot.png などを取り出す。
  セーブステートは `src/disc/states/`（リポジトリに入れない）
- 【数字】主メモリの 0xf60000 付近（と 0xf68000 付近。2コマぶん交互）に、ジオメトライザへの命令の列がある。行列 0x05800000＋float×12、
  物体 0x00800000＋引数×4、焦点距離 0x04800000＋(600,600)。物体の4つ目の引数を g_objTbl（0x1fc8760、2人×5125 語。番号→読み込んだモデルの番地）で
  逆に引くと、5つの写しの全物体がモデル番号になる（01 は 904/904）
- 【絵】行列をカメラの座標とし、x'=x·m0+y·m3+z·m6+m9 …で置いて焦点 600 で写すと、5つとも2人が画面の写真と同じ姿勢の人の形になる（`node pose.mjs disc/states/01_akira_lau out/pose01.png`）
- 【数字】アキラの1コマ: 体 407〜414・416・417・421・422・2452・2454、手 217・259、帯などのひも 2・4・6・30・148・149・2498〜2500、影らしい平たい物 343〜354・415・418・424
- 【数字】命令の列は焦点距離の命令から始め、1つずつ読んで「終わり」（番号 15）で止める。引数の語数: 物体1=4・枠3=6・モード7=1・8=1・焦点9=2・光10=3・
  行列11=12・12=3・LOD22=1、bit31 の立った語は1語。5つの写しで知らない語なしに終わりまで読める。終わりの後ろには前のコマの古い命令が残っている
  （これを拾うと、パイの三つ編みがカメラの手前に浮くなどした）
- 【絵】枠の命令（番号3）の値は上位16bit=x・下位=y と読むと 496×384 の MODEL2 の画面で、中心はその真ん中。写真の絵の範囲（x 9〜630・y 34〜445）に
  引き伸ばして写すと、5つとも2人が写真にぴったり重なる
- 【数字】g_UnitMtxRob0/1Buf は 64B×16（向き3行＋位置、位置の w は NaN）。g_geo+0x40 からはパレット（16bit 色）

## 本体の作り（名前の表で確認。`python3 syms.py disc/x/SLPM_625.47 正規表現`）

- 【確定】本体には名前の表が残っている（6341個）。アーケードの i960 のプログラム（IC12_15.CMP、展開 512KB。戻り命令 0x0a000000 が 1756 個）を
  i960 のエミュレーター（i960Exec*）で動かし、ジオメトライザは PS2 側の代わりの処理（g_geo 0x135a000・m2epiExecGeoCmd・m2epiSetModel）、
  TGP の計算は PS2 の機械語に書き直したもの（cprMtx*・cprMot*）
- 【確定】面を読む divideModel 0x1c9cc0、展開 0x1547c0 など、上のアドレスは名前の表と一致
- 【推測】写しで見る所の候補: g_UnitMtxRob0Buf 0x1689d40・g_UnitMtxRob1Buf 0x1689940（各 0x400）、g_geo、g_objTbl 0x1fc8760

## テクスチャと色

- 【数字】TEX_ROB.MRG の番号とキャラ（写しのテクスチャ用メモリと 768 行一致）: 0 アキラ・1 ジャッキー・2 サラ・3 影丸・4 ラウ・5 ジェフリー・6 パイ・7 ウルフ・
  8 舜帝・10 リオン（660/768 行）。9 はデュラル？（推測）。置き方は 128B×768 行を行の間隔 256B で（1P はページ1、2P はページ0）
- 【数字】面の属性は 1P が塊0、2P が塊1（塊1 はページの bit が反転し、色番号がほぼ +2）。属性の位置は面の頭 bit12-16（符号付き）×8B ずつ進む。
  UV は描いた面ごとに四角 16B・三角 12B、つなぎ方0 の記録も最初の1つ以外は1つぶん進む（本体 0x1c6380。6978 モデル全部で長さが一致）
- 【数字】UV → テクスチャの位置（写しの中の変換済みモデルの ST と小数4桁まで一致）: UV の並びは (P1,P0,A,B)。h0 bit0-2 縦・bit3-5 横の大きさ（32..2048）。
  h2 下位6bit×32＝原点X、次の6bit×32−1024＝原点Y（X≥1024 なら X−=1024・Y+=1024）、bit12＝ページ。UV に +10 して面の最小値を大きさの倍数ぶん戻し、
  ページ内の横＝(u'/8+原点Y)/4・縦＝v'/8+原点X。テクスチャ用メモリの1ページ＝幅 512・高さ 1024 の 4bit（`tex.js` の texCoords・texRam）
- 【確定】面の色 RAM は g_geo+0x40（16bit×1024、i960 の 0x1812000〜）、色の変換表は g_geo+0x840・0x1040・0x1840（R・G・B、各 32行×64、i960 の 0x1810000〜。sysWritePolyCTbl）
- 【絵】色＝色 RAM[h3 の bit6-15] の各チャンネル 5bit を行、明るさを列にして変換表を引く。テクスチャの明るさは h1 の下8bit の番号の CLUT（128B）の t 番目の先頭バイト。
  5つの写しで、2人の服・肌・髪の色が写真と合う（pose.mjs）
- 【確定】パレット（テクスチャの明るさの表）は g_geo+0x2040＋番号×128（m2epiExecGeoCmd が写している所。写しの中の変換済みモデルが参照する表と同じ中身）
- 【数字】明るさ: `node light.mjs 写し` で画素ごとに「法線・光（命令10）・パレットの値」と写真から逆に引いた明るさを並べ、当てはめた。
  パレットの値×(0.88＋0.82×max(0,法線・光))。光の当たらない側で比 0.65〜0.8、当たる側で 1.5〜1.8 まで上がる。素材ごとに係数がばらつく（1P の行 28/30 は環境が強く、2P の 29/31 は拡散が強い）ので本当の式は別（VU1 のプログラム）
- 【絵】影（床に潰した行列の部品）は写真と同じく光の向きに長く伸びる。半透明の黒で描く
- 【絵】07（パイ同士）: 1P＝OBJ_PAI1 の空中蹴り、2P＝OBJ_PAI2（青。42/42）、背景 OBJ_STAGE4（瓦屋根・レンガの壁・龍）。写真と重なる
- 【絵】06（アキラ同士）: 1P＝OBJ_AKI1（紺）、2P＝OBJ_AKI2（白。2P の番号 40/40 が AKI2 にある）、背景 OBJ_STAGE10（獅子の像・塀・龍の箱・床）。写真と重なる
- 【絵】背景: 1P の表のうちキャラのファイルに無い番号は、1つの OBJ_STAGE* に全部ある（01・03〜05＝STAGE1、02＝STAGE2、06＝STAGE10、07＝STAGE4）。属性は塊0。床・塔・建物・木が写真の位置に出る
- 【推測】透明: h0 の bit13 が立った面ではテクスチャの値 15 を抜く（全部の面で抜くとキャラの顔や手に穴が開き、この規則だと開かず木が抜ける）
- 【数字】（v0.3.0 まで）明るさの係数を光の設定ごとに写真へ当てはめていた。v0.4.0 で VU1 の式に置き換えた
- 【絵】設定 31 はパレット 1（値 49〜56）をそのまま明るさにする。色の変換表の 48 列以降は特別な欄（木の緑など）で、そこを引くと写真と同じ緑になる
- 【確定】「パレット」（g_geo+0x2040 の 128B）は GS の CLUT ではなく、VU1 に送る「明るさの段階 B → L」の曲線（VU1 のプログラムで確認）
- 【確定】空・遠景は 3D の物体ではなく、アーケードの2Dのタイルの面（MAME の segas24_tile と同じ作り）。PS2 版は i960 の 0x1000000〜 への書き込みを
  sysScrWL などで g_m2Scr（0x12cd770）へ写す: +0 タイルの表 4面×64×64（値 bit0-13 タイル、bit7-14 パレット＋bit15 で 0x100）、+0x8000 1行ごとの横ずらし、
  +0x9000 設定8語、+0xa810 タイルの絵 512KB（8×8・4bit、下位4bit が左）、+0x8a810 パレット（16bit、bit15 が 0 なら半分、色0 は透明）、+0x8c810 5bit→8bit の表
- 【確定】m2eScrUpdate: 奥の組（面2・3）を先に、手前の組（面0・1 ＝ 体力の棒などの表示）をあとに描く。奥の組は 横＝語2（bit15 で行ごとの表 +0x8800）、
  設定＝語6（bit15 で消す、bit13 で面2・3 を縦につなぐ、下位が縦のずらし）。画面の x → u＝(x − 横) mod 512（m2esiUpdateScrPos）
- 【絵】m2scr.js の scrBack で、01〜07 の写真の空・山・雲・夕焼けと位置が合う。窓（マスク、+0x9010）はまだ使っていない

## ディスクだけで見る（discview.js）

- 【数字】写しのテクスチャ用メモリ: ページ1（1P）の 0〜767 行・各行 128B が TEX_ROB[キャラ]、768〜1023 行が TEX_DFL（01 で全行一致）
- 【数字】色 RAM（g_geo+0x40）は 4つの写しで同じ。FIXPAGE の展開後 0x51000 と 1024 色のうち 899 色が同じ（違う 125 色も写しどうしでは同じ。少し暗くしたような値）
- 【数字】明るさの曲線（g_geo+0x2040）は IC12_15 の展開後 0x78d10 と若い番号（0〜72）が同じ。IC12_15 は 230 本目あたりで終わる
- 【数字】色の変換表（g_geo+0x840〜）はステージ・キャラごとに違う（アキラの肌の行 28: R 68→113→171、ウルフ 95→140→171）。明るさ 0・16・48・63 を折れ点にした直線。
  ディスクのファイルからは見つからなかった（i960 のプログラムが作る。探すのはここで止めた）
- 【絵】肌や服の色の多くは面の色が灰色（28/28/28 など）で、色は変換表の行で付く。だからディスクだけだと灰色がちになる

## ゲームが描いた画面（ソフトウェア描画の写し。`node zsort.mjs disc/states/14_jeffrytest2 out/z.png`）

- 【数字】GS.bin は頭 0x1a9 バイトの後ろに GS のメモリ 4MB。画面は PSMCT32・幅 512（FBW=8）で FBP 0 と 0x80 の2枚（交互に描く2コマ）。
  MODEL2 の 496×384 は画面の (10,34) から。写しの命令の列（sceneRead）はこのうち FBP 0x80 の方のコマ（14・15 とも）
- 【数字】奥行きの表（Zバッファ）は GS のメモリのどこにも無い（0〜2MB は画面2枚、2〜3MB は空、3〜4MB はテクスチャ）
- 【×】重なりの決め方の候補を、ゲームの画面との画素ごとのずれ（候補どうしで食い違う画素だけ）で比べた（14・15）:
  画素ごとの奥行き 11.2・11.7 がいちばん小さい。面を並べて奥から塗る（キー＝頂点の奥行きの max 11.4・12.0、avg、min は大きく悪い）、
  部品ごとに並べる（原点・min・max、裏向きを描かない）12.4〜13.6。どれも画素ごとの奥行きより悪い
- 【確定】腹の帯（v0.7.1）: 命令の列の物体のうち 4つ目の引数が ffffffff のもの（1人1つ、3つ目の引数 4＝1P・0x104＝2P）は、毎コマ作る部品。
  m2epiSetModel は 3つ目の引数の上位16bit が 0 のとき、形＝*g_pM2epiPolWork（0x255dd8）＋0x10e640＋(引数3−4)×4（ファイルと同じ 40B の並び・16 面）、
  属性＝sysGetThdPtr(引数2)（表 0x20e6e0）、UV＝sysGetTpdPtr(引数1)（表 0x20e840）を m2ePolConvModel2DataToPs2 で変換して描く。
  中身はファイルの帯（ジャッキー 2755・属性も同じ）の頂点を胸と腰に合わせて動かしたもの。行列は腰と同じ。これを描かないと腹と背中に隙間が開く
- 【絵】腰（v0.7.1 で解決）: 腹の帯を描くと、ウルフ 2P（15）もゲームの画面と同じく腹が帯の上の縁にかぶさり帯が細く見える。以下は帯を描く前の記録。
  腰: ジェフリー（14）はゲームの画面とほぼ同じ。ウルフの 2P（15）だけ、ゲームでは腹が帯の上の縁にかぶさって帯が細く見え、ページでは帯の上の縁が前に出る。
  どの候補でもこれは直らなかった。ゲームの並べ方は未解明（VU1 の calcZsortMCmdl2 の旗の出どころ＝divideModel〜m2epiExecGeoCmd の詰め直しが読めていない）
- 【数字】明るさ（E）をゲームの画面で確かめた（`BILIN=1 FLIPST=1 POS=10,34,1 REC=out/rec.json node zsort.mjs 写し` で画素ごとの記録）:

## 技（動き）の計算（v0.11 の後に調べた。`node src/motcheck.mjs`）

- 【確定】TGP（コプロ）の呼び方: i960 は FIFO（0x884000＝g11 0x880000＋g12 0x4000）に命令の語（下位8bit が関数の番号。例 0x35806b6b＝107）→ 引数の語 → 答えを読む。
  PS2 の代わりの関数の表は 0x207a50（16B ずつ: 関数・引数の語数・返すバイト数・…、112 個。名前は cprMtx*・cprMot*・cprTri* など）。
  引数は [gp−0x7d90]、答えは [gp−0x7d9c]（gp＝0x25da70）。答えは 16bit で読むこともある（ldis）。TGP のデータ RAM は i960 の 0x900000〜＝PS2 の [gp−0x7d8c]。
  i960 は回転の角度をデータ RAM の 0x90e000〜（輪の番号は 0x5001e4）に直接書き、関数 108〜110（Xrote・Yrote・Zrote）がそれを読む
- 【確定】PS2 版は i960 の重い処理をいくつか自前のコードに差し替えている（sysPatch の表 0x20ab70 → sysExtend の飛び先 0x20b950）:
  0x28184＝sysCopPatchGetFrameDat（コマのデータ）、0x27130＝SmoothInt（つなぎ）、0x16504＝CalcUnitMat（関節の行列）、0x190f0 など＝SetObj（描く）。元の i960 の処理もロムに残っている
- 【確定】キャラの構造体: 1P＝[0x500804]、2P＝[0x500808]（0x2000 バイト）。+0x1a8 技の番号、+0x1aa コマ、+0x800 技の長さ（コマ数）、+0xbd8 動きの表、+4 の bit0＝2P。
  i960 の 0x3acb8〜: 技 m・コマ f を入れて 0x1a1e4・0x26ef0・0x27130・0x27ce0（→0x28184）・0x16504 を呼ぶ流れがある
- 【確定】コマのデータ（0x28184）は FcurveSpl（関数 50）で曲線を引き、手足の目標の位置（+0xb00〜、12B ずつ）と角度（+0xba8・+0xc06、6B ずつ）を作る。
  手足は CalcUnit2Fast（関数 107、2本の骨の IK。骨の長さ 0.212/0.263・0.44/0.39、表 0x296a0）で解き、関節の行列は StUnitMat（関数 53）で
  [gp−0x7dac]（1P の g_UnitMtxRob0Buf 0x1689d40）・[gp−0x7db0]（2P 0x1689940）に 64B×16 で置く
- 【数字】motcheck.mjs: 写しの i960 の RAM から 0x27ce0・0x16504 を動かす（i960 は arcade.js、TGP は PS2 の cpr* を ee.js の EE エミュレーターでそのまま）と、
  24 の写し×2人（投げ・ダウン・リングアウト・勝ちを含む）で 16 個の関節のうち頭（2）以外はほぼ全部ゲームの値と一致（向き・位置とも 0.01 未満）。
  頭と一部（1 など、差 0.03 未満）は、毎コマ少しずつ相手へ向ける持ち越しの値（+0x146〜+0x17c、14B ずつ）のため、同じコマを計算し直すと1歩ぶん進む。
  +0xb00〜+0xc4c を消してから計算しても同じ（動きのデータから計算している）。+0x146〜+0x17c を消すと頭・腕（9〜14）が崩れる
- 【数字】写しの描く命令の列（0xf60000 付近）は関節の行列（UnitMtxRob）より 2 コマほど遅れている（2 コマ前の姿勢を計算して付け合わせると 17 個とも付く写しが多い）。

## VU1 のプログラム（`python3 vudis.py disc/states/01_akira_lau/vu1MicroMem.bin [始め 終わり]`）

- 【確定】VU1 のプログラムは本体の gfxDefaultVU1code（0x1f2000）に入っていて、0x800 バイトごとに 8 バイトの VIF の区切りがある。名前の表の `_$名前`
  を VU の番地に直すと 141 個すべてでセーブステートの中身と一致（vudis.py の labels_from_syms）
- 【確定】calcBrightnessMainMdl2（VU 0x1c18〜）: d＝clamp(光・法線,0,1)、s＝clamp(2d×法線z−光z,0,1)、B＝clamp(拡散×d＋環境＋光沢×s^n,0,127)（FTOI0 で切り捨て）。
  拡散・環境・光沢・回数は VU1 のデータの 0〜31 番（面の光の設定＝面の頭 bit18-22 で選ぶ。変換処理が詰めた頭の下位5bit）、光は 32 番（xyz、w は旗）
- 【確定】m2mdlQuadPoly: L＝VU データ[47＋B]（＋128：頭の bit8 のとき）。47 番からは面ごとに VIF の UNPACK（6280002f）で送られる 128 バイトの曲線（g_geo+0x2040＋h1×128）
- 【確定】m2mdlTransmapBank0〜m2mdlTex: テクスチャありで、光の設定が 10〜12 か L＜48 なら L×8（GS で テクスチャ×17 と掛ける）、それ以外は 48＋テクスチャ（特別な欄）。テクスチャなしは L×16
- 【数字】この式（build.js の buildBright・buildLuma）で、7つの写しの写真とのずれが当てはめの式より減る（light.mjs）
- 【確定】m2mdlSetSameZval: 1つの部品の面はみな同じ Z で、ファイルの順に塗る（面の頭の bit2 は全部 0）。だから貼りもの（属性 h1 の上位バイト≠0。目・眉は光の設定 31）が肌に勝つ。
  ページは貼りものの面の奥行きを 0.00002×z だけ手前にずらして真似る（vgl.js。ずらす量は【推測】）
- 【絵】顔の一覧: `node faces.mjs [out/faces.png]` はページそのもので、7つの写し×2人の頭（貼りものを持つ部品のうち高い所にあるもの。カメラの座標は y が上）を4方向から撮って並べる。
  v0.4.2 で 10 人（デュラル以外）の顔が出るのを確認。ウルフの顔の赤い筋はゲームの写真にもある（隈取り）
- 【絵】顔の寄り（ページを通さない）: `node faceshot.mjs disc/states/06_akira_akira out/face.png 0 412 15`（1P の頭 412 を4方向から）。v0.4.1 でページのアキラ・パイの顔も確認
- 【数字】v0.6.0 の式での写真とのずれ（light.mjs → lighterr.mjs）: 全体 8.22（01 9.57・02 6.39・03 7.14・04 9.38・05 7.33・06 8.75・07 10.96）、偏り +0.56。
  ずれはテクスチャの値に沿う: 値 0〜3 は予測が暗すぎ（−4〜−7）、12〜15 は明るすぎ（+6〜+10）。写真から逆に引いた「テクスチャの明るさ」は t×17 ではなく おおよそ 98・…・78（t=4）〜190（t=15）
- 【推測】テクスチャの 4bit の値は GS の CLUT で直線でない明るさに変わっている。c(t)＝52＋9t に当てはめると全体 8.22→7.40（06 は 8.75→8.88 と少し悪い）。当てはめなのでページには入れていない
- 【×】その CLUT を GS.bin（灰色の 16 色、CT32・CT16）と主メモリ（灰色・α の段々）で探したが見つからなかった。次は m2epiInitTransTexPacket・m2mdlTex の TEX0（CBP）から追う
- 【推測】光沢の回数（w の下位3bit）の扱いは VU の実行の遅れが絡むので s^8 と近似。7つの写しでは結果に影響しなかった
