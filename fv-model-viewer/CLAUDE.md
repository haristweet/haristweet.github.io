## 分かっていること

各項目の頭の札: 【確定】本体のコードで確かめた　【数字】全ファイルで数を数えて確かめた　【絵】描いて見て確かめた　【推測】まだ確かめていない　【×】試して合わなかった

- 【数字】ディスクの BIN.CVM の中に、アーケードのロムが入っている: ROM_CODE1（展開 512KB。i960 の戻り命令 0x0a000000 が 1956 個）・ROM_CODE2（1MB）・
  ROM_DATA（16MB）・ROM_POL（12MB）・ROM_TEX（8MB）・ROM_EP1/2（各 1MB）。どれが何かは【推測】（名前から: 形・テクスチャ・データ）
- 【数字】本体の名前の表は消されている（.symtab が空。VF2 は 6341 個残っていた）。文字列には VF2 と同じ M2EPOL などが残る
- 【数字】計算用チップ（アーケードは Model 2B の SHARC）の代わりの関数の表が本体の 0x23fc20 にある（16B ずつ 112 個。VF2 は 0x207a50 に 112 個）。
  引数の語数・返すバイト数が VF2 と同じものが 97/112
- 【数字】モデルのファイル（OBJ_*.CMP を展開したもの）は VF2 と同じ形式: 57 ファイルとも最後のバイトまで区切れ、面の読めないモデルは 0（VF2 の obj.js）
- 【絵】OBJ_ROB00 の部品は手・腕・脚・胴・頭らしい形。1849〜1922 はお椀の形が段々と粉々になる並び（鎧が壊れる所？【推測】）
- 【数字】描く命令の列: 主メモリの 0x1288000 付近から（焦点距離の命令 0x04800000 の値は 480。VF2 は 600）、0x8000 おきに同じ形の列がいくつもある。
  VF2 と同じ番号（物体1・枠3・モード7・焦点9・光10・行列11・LOD22）に加え、4＝[番地][語数 n][n 語]・13 と 16＝1 語、で 4 つの写しとも終わり（15）まで読める
- 【数字】番号 → 読み込んだモデルの番地の表は 0x1f834f0（2 人 × 5413 語。VF2 は 0x1fc8760 に 2 人 × 5125 語）。表の番地の先の、読み込み済みのモデルの中に、
  ファイルのその番号のモデルの頂点（小数 3 つ）がある: 4 つの写しで前半 1994/2000、後半 625/625。読み込み済みのモデルの頭は VF2 と同じ（…00000060 … 01000030）
- 【絵】行列をカメラの座標とし、焦点 480 で写す（VF2 と同じく x は 622/496、y は 412/384 倍して 640×480 の真ん中へ）と、4 つの写しとも 2 人と背景（柵・建物・ヘリコプター・ロープ）が写真に重なる
- 【絵】GS.bin の画面は VF2 と同じ読み方（頭 0x1a9 の後ろに 4MB、PSMCT32・幅 512、FBP 0 と 0x80）で、続いた2コマ（タイマー 26・25）が出る（grace）
- 【数字】キャラのファイル（写しで描いた番号をいちばん多く含むもの）: ROB00 ジェーン・ROB01 グレース・ROB02 ハニー・ROB03 トキオ・ROB04 バーン・ROB05 ピッキー・ROB06 ラクセル・ROB07 サンマン。
  ステージ: STG02＝round1（グレース対ピッキー）、STG08＝塔（ヘリコプター）。OBJ_COMMON からも 28〜32 部品（影など？【推測】）
- 【数字】2P の色のファイルは 1P の番号＋13（ラクセル 06→19・バーン 04→17・グレース 01→14・ピッキー 05→18・ハニー 02→15・ジェーン 00→13・サンマン 07→20・トキオ 03→16）。
  ステージ: STG01（ピッキー・ハニー）・STG02（ラクセル・ジェーン・サンマン・トキオ）・STG08（塔）
- 【絵】写し 14 個のうち、構え・ダウン・鎧が壊れた所は写真と重なる。ラクセル同士の投げ（動きが速い）は、最初に見つかる命令の列（0x1288000）では 2 人の位置が写真・GS の画面とずれる
- 【数字】命令の列は 0x1288000・0x12a8000・0x12c8000 から 0x8000 おきに 4 つずつ、計 12 個。中身は別々のコマ（ラクセルの投げで 2P の奥行き 4.79〜5.87）。
  列の頭（焦点の命令の前 0xc8 バイト）は前のデータの残りで、コマの番号は無い。列の番地を指す語も見つからない（番号で持っている？）
- 【絵】ラクセルの投げでは、いちばん奥行きの進んだ（いちばん新しいと思われる）列 0x12c0000 が GS の画面に近い（`BUF=12c0000 node pose.mjs …`）。
  【推測】ゲームは最新の列を画面に出している。どれが最新かをゲームがどこで決めているかはまだ（教訓3: 当て推量で選ばず、置き場所を探す）
- 【数字】12 個の列の中身の時間の順（ラクセルのダウンで 2 人の位置の和が単調に動くので並べられる）: 列の番地の順に t2 t3 t0 t1 | t2 t3 t4 t1 | t2 t3 t4 t5。
  4 つずつの組の同じ場所（s0〜s3）には同じコマか、より新しいコマが入る。いちばん新しいコマはラクセルのダウンで 0x12e0000（組3 の s3）、投げで 0x12c0000（組2 の s3）で、決まった番地ではない
- 【×】0x12c0000 を持つ語（0xef87c4 など）は、列を管理する値ではなく色（01RRGGBB）の並びだった。本体に列の番地を作る定数（lui 0x128〜0x12f）はあるが、0x187818〜 は別の所への写し（0x1471c0）
- 道具: `python3 mipsdis.py disc/x/SLPM_626.06 始め 数`（本体の MIPS。capstone を使う）
- 【数字】色とテクスチャの塊（VF2 の g_geo）は 0x12e7a80。テクスチャのファイル TEX_ROBnn（128B×768 行）が 1P は +0xa040+0x40000、2P は +0xa040 に行の間隔 256B で載っている（grace）。
  +0x840〜 の色の変換表は明るさで折れ線状に増える行（28 行目がキャラごとに違う）、+0x40 の色 RAM は 16bit の色（0x8421 など）で、VF2 と同じ並び
- 【絵】VF2 の色の付け方（build.js・明るさの式・光は VU1 のデータ）をそのまま当てると（`node colorshot.mjs 写し`）、服・肌の色は写真と合う（grace・bahn）。
  テクスチャは VF2 の引き方だと縞だらけ（下の v 以降で直した）
- 【数字】読み込み済みモデルの ST は (UV＋7)÷区画の大きさ（区画ごとの 0〜1。VF2 は UV＋10）。部品 915 の UV (317,70) が 0.3164/0.1504
- 【確定】アーケードのテクスチャの展開（`node arcadetex.mjs セット,… out/arc.png`、fvarc.js）: FV の読み込みの流れ（ROM_CODE1 の 0x4b5ec〜）は VF2 の 0x4bd60〜 と
  命令単位で同じ。関数は VF2 0x4d16c→FV 0x4ca74・0x4c180→0x4ba2c・0x4cb64→0x4c470・0x4cd18→0x4c620・0x4c9dc→0x4c2a0、表 0x4c120→0x4b9c0。
  main_data はディスクの ROM_DATA（そのまま 0x2000000〜。表 [0x230000c]・[0x2300008] も VF2 と同じ場所）。
  違い: テクスチャ RAM の書き先の頭を RAM の [0x500254]（ページ0）・[0x500258]（ページ1）から読み、16bit の語を 2 バイトおきに書く（VF2 は定数 0x12200000・0x12600000 で 4 バイトおき）。
  段の進みは 0xc0000（VF2 は 0x180000）。セット 3＋4 で 430 万命令・0.3 秒
- 【数字】PS2 のテクスチャのファイル（TEX_ROBnn、128B×768 行）の行 r・横 x ＝ アーケードの RAM の (x＝r を偶数に丸めたもの, y＝2x＋1＋512×(r&1))（ページ1。セット 3＋4＝ROB01 グレース。
  特徴のある 16 テクセルの並び 2 か所がそれぞれ 1 か所だけに一致）。縦横とも 1 つおきに間引き、RAM の y≥512 を奇数の行に入れている
- 【絵】面のテクスチャ: アーケードの RAM の (x, y)＝(X＋(v＋7)/8, Y＋(u＋7)/8)（X＝(h2&63)×32、Y＝(h2>>6&63)×32−1024）を上の対応で PS2 のテクスチャ用メモリから引く（tex.js）と、
  ピッキーの服・グレースのブーツ・ハニーの服が写真とほぼ同じに出る。まだ合わない: ステージ（置き場所が別）・グレースの髪が白い・バーンの肩とコートの縞
- 【数字】ステージのテクスチャ: アーケードのセット 18＋n（OBJ_STGn）。PS2 のテクスチャ用メモリと、RAM の y＝1024〜1535 の奇数・x の偶数の所で 100% 一致
  （grace＝STG02→セット 20・塔 STG08→26・picky STG01→19。各 26 万テクセル）。そこの PS2 の置き方は ページ×0x40000＋(x>>1)×512＋256＋((y−1024)>>2)。
  キャラの置き方（上）と 1 つの式にはならない（区画ごとに振り分けている？）。PS2 のテクスチャで描くのはやめ、アーケードのテクスチャを直接引く
- 【絵】`ARC=1 node colorshot.mjs 写し`（キャラはセット 2n+1・2n+2、2P の色 n≥13 は n−13 で 2P はページを入れ替え、ステージは 18＋n）: grace・bahn・picky 同士で、
  髪・看板の文字・床の木目・PEPSI の板・フェンス・2P の色が写真とほぼ同じ。違う所: バーンのコートに赤い縞（写真は無地）・空が無い（2D の面、VF2 の m2scr.js にあたるもの）
- 【数字】PS2 のテクスチャ用メモリの並び（全体）: アーケードの RAM（ページごとに横 1024・縦 2048）の (x, y) → ページ×0x40000＋(x>>1)×512＋((y>>9)&3)×128＋((y&511)>>2)、
  ニブルは (y>>1)&1。1 行 512B が「y 0〜511・512〜1023・1024〜1535・1536〜2047」の 128B ずつ。前に書いた「ファイルの奇数の行は r×256」は、ファイルの中の並びとしては正しいが、
  メモリでは (r−1)×256＋128（偶数の行の後ろ）。tex.js の texRam を直した
- 【数字】写しの PS2 のメモリと一致するアーケードのセット（94〜95%。残りは段の小さい版の所など）: キャラ 2k+1・2k+2（2P はページ0）と、共通のセット 36（ページ1）だけ（bahn・grace・picky 同士）
- 【絵】バーンのコート（部品 2405、173 面）の格子柄は、裏地の面（色 0x2f40・面 113〜158。表の面 37〜91 と UV が同じで頂点の並びが逆）が表に出ていたもの。
  ページも colorshot も裏向きの面を描いていた。キャラの面は裏向きなら描かない（build.js の特別の値 +1024、vgl.js で gl_FrontFacing が偽なら捨てる。colorshot は画面の回り方 d>0 を捨てる）で直った（v0.4.2）。
  逆の向きで捨てると体の内側が見える。【確定】v0.4.3 で、捨てるのは面の頭の bit17（両面の旗）が 0 の面だけに（MAME の model2_v.cpp の check_culling。表か裏かは 法線・頂点 ≥ 0 が表）。
  【×】同じ頂点の面を「重ねる面」から外す（向きで区別する）だけでは変わらなかった（colorshot は重ねる面を使わないため）
- 【数字】空・遠景の 2D の面（VF2 の g_m2Scr）: FV は 0x11fb1c0（5bit→8bit の表 3 色が +0x8c810 に並ぶ所から逆算）。VF2 の m2scr.js の並びのうち、
  タイルの表（+0、面2 の空はタイル 0x1e00〜0x2727）・設定（+0x9000）・パレット（+0x8a810）は合う（空の青・雲・夕焼けの色と、雲の大まかな位置が写真どおり【絵】）。
  タイルの絵（+0xa810）の並びが VF2 と違い、そのままでは点々になる【×】
- 【確定】タイルの絵を写す関数は本体の 0x184800（と 0x184940 など）: i960 の番地 A から off＝A−0x1080000、書き先＝塊＋0xa810＋D、
  D＝((off&0x1ff)>>2)<<6 | (off&3) | ((off>>12)&15)<<2 | (((off>>9)&7)＋((off>>16)<<3))<<13。16 バイト（4 語）を D・D+4・D+8・D+12 へ、
  各語はニブルを入れ替え（0x0f0f0f0f）、16bit の中でバイトを入れ替えてから書く。アーケードのタイルの並べ方（1 タイル 32 バイト？）と合わせると隣と重なるので、
  アーケード側の並べ方をまだ読み違えている。続きはここから（止めた: 2026-09-27、1 時間）
- 【絵】毎コマ作る部品（v0.2.0）: 命令の列の物体で 4 つ目が 0xa のもの。1 つ目＝テクスチャの座標の塊・2 つ目＝属性の塊（読み込んだ OBJ_ROBnnR.BIN の中。R の BIN は .CMP を展開したものと同じ中身）、
  3 つ目＝そのコマの形（0xe93200・0xe93600。40B の面の記録）。塊の長さは塊の前の語。1P・2P は描く順（tokio 同士では 2 人とも同じ属性の塊を指す）。14 の写しで 1 人 1 つ・16 面
- 【数字】DMA の状態（eeHwRegs.bin）はどの写しも同じ（toSPR の MADR 0x12e82c0 ＝ 12 個の命令の列の範囲のすぐ後ろ、VIF1 0x33e7c0）。どの列が画面のコマかはここからは決まらない
- 【数字】ディスクだけで見る（v0.3.0）の色の材料: 面の色＝ROM_DATA の 0x100000（写しの色 RAM と 1023/1024 色が同じ）、明るさの曲線＝ROM_EP1 の 0x266e0（写しの 256 本のうち若い 7 本が同じ）

## 技（動き）（2026-09-27。VF2 の motion.js と同じ作り。`src/motion.js`・`src/ee.js`）

- 【確定】本体の gp は 0x292170（起動処理 0x100170 で入れる）。前に 0x29213c と書いていたのは誤り（その値でたまたま [gp−0x7cf4] がそれらしい番地だった）。
  TGP の引数 [gp−0x7cf4]・答え [gp−0x7d00]・データ RAM [gp−0x7cec]（本体の命令で確かめた）。関節の行列: cprMtxStUnitMat（0x18eac0）が
  [[gp−0x7fb8＋4×(引数0&1)]]＋(引数1/12)×64 に書く（2 回たどる。VF2 は 1 回）。引数0 は [g7+4]
- 【確定】技の表は ROM_EP2（i960 の 0x6c00000〜）。先頭の語＝技の数 1053、0x6c00004＋技×4＝動きのデータの番地（ROM_DATA 0x2c〜0x2e… か ROM_EP2 の中）。
  データの先頭 16bit＝コマ数。写し 28 人分で キャラの +0x800 と全部一致
- 【確定】キャラの構造体は VF2 と同じ（[0x500804]・[0x500808]、+0x1a8 技・+0x1aa コマ・+0x800 長さ）。i960 の関数: 技を始める 0x1b880・0x29d08、つなぎ 0x29f48、
