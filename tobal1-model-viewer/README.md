# トバルNo.1 モデルビューア

PlayStation 版『トバルNo.1』のディスクイメージを読み込み、中のキャラクターの3Dモデルを
ブラウザで回して見るビューア（非公式）。

**https://haristweet.github.io/tobal1-model-viewer/**

姉妹版の [トバル2 モデルビューア](https://haristweet.github.io/tobal2-model-viewer/) から、
ディスクの読み取り・ゲーム独自の圧縮の展開・モデルの組み立て・描画をそのまま持ってきている。
違うのは **中身の位置を決め打ちしていない** ところ。トバル2 では解析で分かった値
（ファイル表の位置 `0x800CD660`、キャラごとのモデル番号）を直接書いていたが、
No.1 はまだ解析していないので、読み込んだディスクから実行時に探しにいく。

## 使い方

1. 手持ちのトバルNo.1 のディスクイメージをページにドロップするか、「ファイルを選ぶ」で選ぶ
   - `.chd`（MAME の圧縮形式・v5）
   - `.bin`（2352バイト/セクタの生イメージ、または 2048バイトの ISO）
   - ディスクから取り出した実行ファイル（`SLPS_004.00` など）とデータのまとまったファイルの2つ
2. 左の一覧からファイルを選ぶと、その中身をモデルとして組み立てて表示する
3. うまく出ないときは「解析」タブの内容を見る（そのままコピーできる）

ドラッグで回転、右ドラッグ／Shift＋ドラッグで移動、ホイールで拡大、ダブルクリックで視点を戻す。
タッチは1本指で回転、2本指で移動と拡大、ダブルタップで戻す。
背景の色は8種から選べて、「スクショを保存」で PNG（透明背景・キャラだけ切り抜きも可）。

ゲームのデータはこのページに一切含まれていない。読み込んだファイルはブラウザの中だけで読み取り、
どこにも送信しない。

## 中身

`index.html` の1枚のみ。外部ライブラリもビルドも無い（WebGL 直書き）。

### トバル2 から持ってきたもの（そのまま）

- ディスク: ISO9660 の読み取り。CHD はハンクの目次（ハフマン符号）を解いて `cdlz`（LZMA）と
  `cdzl`（Deflate）を展開する。`cdfl`（FLAC）と差分形式には未対応
- 圧縮: ゲーム独自の圧縮（先頭 `0x0b`、4bit モードの256バイト単位ブロック）の展開
- 入れ子: 先頭に「部分の数」と「各部分の位置」が並ぶファイルの分解
- モデル: 表示命令の列（関節選択・頂点変換・ポリゴン命令）をたどって三角形にする
- 骨格: 骨の長さの表と親子関係から T ポーズを組む
- テクスチャ: VRAM 転送列（4bit/8bit 画像とパレット）を仮想 VRAM に置き、パレット引きはシェーダで行う
- BGM: XA-ADPCM（4bit ステレオ 37.8kHz）の展開と Web Audio での再生

### No.1 用に作り直したもの（自動検出）

- **ディスクの中身**: 名前を決め打ちせず、ISO のディレクトリをたどって全ファイルを並べる。
  `SYSTEM.CNF` の `BOOT=` から実行ファイルを決め、音声・動画を除いていちばん大きいファイルを
  アーカイブとみなす
- **ファイル表さがし**: 実行ファイル全体を 8バイト単位で走査し、
  「位置と大きさが隙間なく並んでいるところ」を探す。1件の形は2通り試す
  （`位置 / 大きさ<<8|種類`＝トバル2 と同じ、`位置 / 大きさ`）。表の途中の空きスロット（0埋め）は
  並びを切らさず、末尾に続く 0埋めは表に含めない。候補は「詰まり具合」で並べ、
  「解析」タブから手で切り替えられる。候補の順番は、**その表が指す先を実際に何件か読んで**
  トバルのファイル（入れ子・圧縮）になっているかで決める（詰まり具合だけで決めると、
  たまたま数件そろっただけの短い並びが勝ってしまう）
- **アーカイブさがし**: どのファイルがデータのまとまりかも決め打ちせず、音声・動画
  （`.XA` `.STR` `.DA` など）を除いた大きいファイルを候補として持ち、実際に中身を読んで決める
  （「解析」タブから手でも変えられる）。名前も手がかりにする（`ALLBIN.BIN`、`.BIN` / `.DAT` など。
  `BGM/` `SOUND/` の下は下げる）
- **ファイルの見分け**: 先頭1セクタだけ読んで、入れ子・圧縮・TIM・そのままを見分ける。
  部分0が `0x0b` で始まる入れ子を「モデルらしい」とみなす。種類ごとに数件ずつ調べて一覧に出し、
  「全部のファイルを調べる」で全件まわす
- **テクスチャの部分**: 何番目の部分かを決め打ちせず、VRAM 転送列として筋の通る部分を探す
- **モデルの並びを自分で合わせる**: トバル2 の並び（描画命令が `0x20` から、頂点/面/色の位置が
  ヘッダの語 5/4/7）で組めなかったら、ブロックを見て並びを割り出す。描画命令の開始位置は
  **ヘッダの語が指す先**も候補にし、頂点・面の置き場所は「座標が人の大きさに収まるか」
  「頂点番号が範囲に入るか」「中身が詰まっているか」で選ぶ。三角形が出ても1点に潰れていたら
  当たっていないとみなす
- **骨格**: トバル2 のつなぎ方をそのまま使う。合わないときのために「関節を使わない」
  （モデル内の座標をそのまま出す）に切り替えられる
- **BGM**: XA のセクタのサブヘッダ（チャンネル番号・サブモード）を先頭64セクタだけ読んで、
  何本が何セクタおきに入っているかを数えてから鳴らす
- **テクスチャ（No.1 の形）**: `u32 長さ ; u16 x ; u16 y ; u16 幅 ; u16 高さ ; データ[幅×高さ×2]`
  の繰り返し。`長さ = 12 + 幅×高さ×2` が成り立つ。列の途中に 8 バイトの目印（`0x10, 0x08`）が
  挟まるので、合わない語は 4 バイトずつ読み飛ばして拾い直す
- **モデル本体がどの部分かを探す**: トバル2 は必ず部分0 が本体だったが、No.1 は
  `[8, 8, 85440]` のように**後ろの部分**に入っていることがある。展開できた部分を
  大きい順に試して、三角形が取れたものを採る
- **アーカイブを直接さらう**: ファイル表の形が分からなくても、アーカイブの中を 2048 バイトごとに見て
  「ファイルの先頭らしいところ」（`0x0b` で始まる圧縮、または入れ子の目次）を拾う。
  表からモデルが出てこないときは自動でこちらに切り替わる。さらった結果から、
  実行ファイル内のファイル表の位置と1件の長さを逆算して「解析」に出す
- **解析タブ**: 実行ファイル・アーカイブ・表の候補・種類ごとの件数・選択中のファイルの内訳
  （部分の大きさ、展開後の長さ、描画命令の内訳、三角形の数、骨の数）をテキストで出す

## 状態

**トバルNo.1（SLPS-00400）のディスクで確認中。** ディスクは読めていて、実行ファイル
`SLPS_004.00` と `ALLBIN.BIN`（24.22 MB、トバル2 と同じ名前）を見つけるところまで来ている。
v0.1.3 でアーカイブの選び方を直したところ。

途中、トバル2（`SLPM_860.33`）のイメージでも通しており、**正解と答え合わせができた**おかげで
探索の不具合が3つ見つかっている（下の更新履歴）。

分かっていること（実測）:

- **圧縮形式はトバル2 と同じ。** アーカイブ内のファイルの先頭が `0b 84 de 00` で、
  トバル2 の展開処理のヘッダ（`0x0b` ＋ 展開後の大きさ）として読める
  （圧縮 17,740 バイト → 展開後 56,964 バイト）
- アーカイブの先頭には `dummy` という詰め物が入っている
- **テクスチャファイルの署名**: 先頭16バイトが `語0 = 組数`、`語1 = 0x10`、
  `語2 = 8 か 9`、`語3 = 0x2C（16色）か 0x20C（256色）`。実物 24件で
  「語0 × 2 = 転送枚数」が一致（8→16、20→40、25→50、41→82 …）
- **ファイル表の1件は 20 バイト。** 8バイト刻みで読んだとき、中身のあるエントリが
  `#35, #40, #45, #50 …` と5の倍数に並ぶ（8×5 = 40 = 20×2）。
  さらった結果から逆算した「1件 20 バイト」とも一致する。位置は record の先頭にある
- **音声は `VAGp`（PS1 の VAG 形式）。** 効果音・ボイスが多数
- **面の形**: 12バイトで1枚の三角形。`u32 ×3` が頂点番号で、値は**4倍**で入っている
  （`18 00 00 00 14 00 00 00 10 00 00 00` → 24,20,16 → 頂点 6,5,4）。
  面の領域 768 バイト ÷ 12 = 64枚で、ヘッダの `20+11+33` と一致する
- **モデルの部品の形**（実物 sector 5927 で確認、別の部品でも一致）:
  `面の位置 / 頂点の位置 / 法線の位置 / 色の位置` の4つに続いて、頂点数・法線数・面の数×4種。
  `+0x38` から 頂点（int16 x,y,z,余り）→ 法線 → 面 → 色（u8 r,g,b,余り）が隙間なく並ぶ。
  面は先の2種が8バイト、後の2種が12バイト
- **モデルは `0x90000000` で始まる。** 183件のふるい分けで判明。種類B（`語1 = 0x3C か 0x34`、
  4部分、展開後 30〜43KB、sector 5529〜9289）がキャラクターのモデルらしく、
  種類A（`語1 = 0x14`、109部分、展開後 4KB 前後、sector 6016〜6312）は別のデータ
- **大きいファイルは全部テクスチャだった。** 上位24件（34KB〜214KB）がすべて
  テクスチャの集まり。モデルはもっと小さいところにある
- **テクスチャは読める。** 84KB のファイルから転送 24枚を取り出せた
  （`(416,486) 16×1` パレット → `(624,0) 16×131` 画像 → `(288,504) 16×1` パレット →
  `(678,258) 12×64` 画像 … とパレットと画像が交互）
- **テクスチャの形が分かった。** 84KB のファイル（sector 6408、本体は部分2、展開後 189,680B）は
  モデルではなく**テクスチャの集まり**だった。`u32 長さ ; u16 x,y,幅,高さ ; データ` の繰り返しで、
  1枚目が 16色パレット（`(416,486) 16×1`、BGR555 に最上位ビット）、2枚目が画像
  （`(624,0) 16×131`）。`長さ 0x2C = 12+16×1×2`、`長さ 0x106C = 12+16×131×2` と
  2箇所で検算が合う。本文が `ee ee` `88 88` だらけなのは 4bit 画像だから
- **モデル本体は部分0 とは限らない。** 84KB のファイル（sector 6408）は
  部分の大きさが `[8, 8, 85440]` で、部分0 は展開して 4 バイトしかなく、本体は部分2 だった
- アーカイブの中身は、直接さらった範囲で **183件**（入れ子 54 / 圧縮 15 / 入れ子＋圧縮＝モデル候補 114）
- **モデルの形はトバル2 と違う。描画命令の文法も通用しない**（`0` や `5` で始まり、
  トバル2 の命令表に無い）。展開したブロックの頭が
  `0x90000000 0x00000014 0 0 0 | 0x0000047C 0x0000017C 0x0000047C 0x00000E7C | 5 1 0 6 8 …`。
  先頭に `0x90000000` の印があり、語1（`0x14` ＝ 20）の先に置き場所が4つ並ぶ。
  トバル2 は先頭に印が無く、ヘッダの語 4/5/7 が面/頂点/色を指していた。
  区画は `0x17C`(380) / `0x47C`(1148) / `0xE7C`(3708) / 末尾(4240)。`0x14` からは
  24バイトの繰り返し（`5 1 0 6 8 8` / `5 1 0 12 8 16` …）が並ぶ。
  `0x47C` の中身は `(128, 0, -20)` `(0, 0, -149)` と、頂点らしく読める
- **ファイル表の1件は 8 バイトではない。** 8バイト刻みで読むと、ファイルらしい
  「位置・大きさ」の間に `0x8000EA00` `0x800CC09C` といった RAM のアドレスが挟まる。
  トバル2（1件8バイト = 位置 ＋ 大きさ<<8|種類）とは形が違う

ディスクの中身（実測）:

- `ALLBIN.BIN` 24.22 MB — データのまとまり（トバル2 と同じ名前）
- `SLPS_004.00` 756 KB — 実行ファイル（text=0x80010000、size=0x000BC800）
- `OPENING.STR` / `UDAEND.STR` — 動画
- `BGM/*.DA` 24本 — BGM。CHD では音楽トラックが FLAC（`cdfl`）で圧縮されていて未対応なので、
  いまは鳴らせない（`.XA` ではないため BGM の欄も出ない）

トバル2 は解析済みでファイル表の正解（`0x800CD660` / 1362件）が分かっているため、
このビューアは**トバル2 のディスクを入れると正解と照らし合わせて表示する**ようにしてある
（「解析」タブに「正解のファイル表」と、候補への `✓正解` 印が出る）。
No.1 の前に探し方が正しいかを確かめられる。

作った環境にディスクイメージが無いので、コード自体の確認は合成データで行っている
（ファイル表さがし・候補の並べ方・入れ子・独自圧縮の展開・モデルの組み立て・描画・一覧・
解析タブを、実際にブラウザで動かして確認済み。テスト31件）。

うまく出ないときの見方。

- 一覧は出るがモデルが出ない → 表示命令かテクスチャの形が違う。「解析」の内容が手がかりになる
- ファイル表が見つからない／中身 0% ばかり → 表の形が違うか、アーカイブの選び方が違う。
  「解析」の「大きいファイル 5件」と「表の先頭 8件」を見る
- 「ディスク直読み」に切り替えると、ディスクのファイルを直接見られる

## 未対応

- 動きの再生。トバル2 版は実行ファイルの処理をページ内の MIPS＋GTE エミュレータで
  動かしているが、呼び出すアドレス（`0x80048a40` など）がトバル2 専用なので、
  No.1 の解析ができるまで入れていない
- キャラクターの名前。ファイル番号でしか呼べない（どの番号が誰かは解析待ち）
- 勝利ポーズ・技名・投げの2人表示・動画の書き出し

## 更新履歴（Changelog）

- **v1.0.0** (2026-09-17) — **面の形が分かった。** 面のバイト列を出してみたら、
  `18 00 00 00 | 14 00 00 00 | 10 00 00 00` ＝ 24, 20, 16 と、すべて4の倍数だった。
  4で割ると 6, 5, 4 で頂点番号になる。つまり **面は 12バイトで1枚、`u32 ×3` が頂点番号で、
  値は頂点番号の4倍**（PS1 でよくある、掛け算を省くための持ち方）。
  面の領域 768 バイト ÷ 12 = **64枚ちょうど**で、ヘッダの `20 + 11 + 33 = 64` と一致する。
  `10, 20, 11, 33` の4つを面の数だと思って 8バイト／12バイトに割り振っていたのが間違いで、
  面はすべて 12バイト均一、`10` は別の意味の数字だった。

- **v0.9.3** (2026-09-17) — 実物で 8部品すべて組めて三角形 370枚まで来たが、
  **別々の位置が 60点しかなかった**（8部品で約380頂点あるのに）。つまり面の中の
  頂点番号の読み位置が違う。「頂点番号が範囲に収まる」だけで読み方を選んでいたため、
  同じ頂点ばかり指す読み方でも通ってしまっていた。**使われた頂点の種類数**も点数に入れ、
  面の種類（8バイト×2種・12バイト×2種）ごとに読み方を選ぶようにした。
  あわせて、**面のバイト列を「解析」に出す**ようにした（区画のダンプは先頭と末尾しか
  出しておらず、面は真ん中にあって見えていなかった）。

- **v0.9.2** (2026-09-17) — v0.9.1 でも画面が真っ暗だった（三角形 370・広がり 199・8/9 部品は
  出ていた）。**カメラの半径の求め方が原因**。軸ごとの 2〜98% で枠を決めると、頂点が1か所に
  固まっているとき帯がゼロ幅になり、半径が 1 になって遠くが切り落とされる。
  **中心は各軸の中央値、半径は「中心からの距離の 98% 点」**で決めるようにした。
  つぶれた三角形の法線が出ずに色が壊れるのも直し、解析に「別々の位置が何点あるか」を追加。

- **v0.9.1** (2026-09-17) — v0.9.0 で 8部品すべて組めて三角形が 186 → **370** に増えたが、
  画面には何も出なかった。カメラの枠を頂点の最小・最大で決めていたため、**1点でも飛んだ頂点が
  あるとモデルが点になってしまう**。各軸の 2%〜98% で枠を決めるようにし、
  座標が人の大きさ（±8000）を外れる面は落とすようにした。
  どの部品が変なのか分かるよう、**部品ごとの座標の範囲**を「解析」に出し、
  画面の下の表示にも「広がり」と部品数を出すようにした。

- **v0.9.0** (2026-09-17) — **実物のトバルNo.1 から三角形が出た**（sector 5927 で 186枚）。
  ただし 4/9 部品しか組めていなかった。原因は、頂点数・法線数をヘッダの決まった場所から
  読んでいたこと。実物には**頂点51・法線51 の部品と、頂点47・法線45 の部品が混ざっていた**。
  位置の差から数を割り出すようにし（`頂点数 =（法線の位置 − 頂点の位置）÷ 8`）、
  面の数4種も場所を決め打ちせず「8バイト×2種 ＋ 12バイト×2種 が面の大きさに一致する並び」を
  頭から探すようにした。

- **v0.8.1** (2026-09-17) — v0.8.0 で**モデルを読む処理をページに入れ忘れていた**のを修正
  （`t1ObjectOffsets is not defined`）。テストの束には入れたのに、ページの組み立ての一覧に
  足していなかった。同じ取りこぼしを防ぐため、**組み立てに入っていない `.js` があれば
  ビルドで止める**ようにし、**トバルNo.1 の形のモデルをページ側で通しで組む確認**
  （ブラウザで実際に描いて画素を数える）も追加した。

- **v0.8.0** (2026-09-17) — **トバルNo.1 のモデルの形が分かったので、専用の読み方を実装した。**
  実物（sector 5927、展開後 42,744B）のダンプから、部品ひとつの形が読めた。

  ```
  +0x00 面の位置   +0x04 頂点の位置   +0x08 法線の位置   +0x0C 色の位置
  +0x1C 頂点の数   +0x20 法線の数     +0x24 面の数×4種   +0x34 0
  +0x38 頂点 int16 x,y,z,余り → 法線 → 面 → 色 u8 r,g,b,余り
  ```

  面は先の2種が8バイト、後の2種が12バイト。`0x6F10` の部品（51頂点、面 10/20/11/33）で
  `10×8 + 20×8 + 11×12 + 33×12 = 768` が色の位置とぴったり合い、`0x7644` の部品
  （48頂点）でも一致した。部品の位置はファイルの先頭に「個数 ＋ その数だけの位置」の組で

## v1.2.0 — 面の本当の形が分かった（法線つき）

v1.1.0 で出した「面の中身」のダンプで、1枚の面の形が完全に決まった。

```
0c 00 00 00  08 00 00 00  04 00 00 00  00 00 00 00   頂点番号 u32 ×4（どれも4倍）
25 02 63 f8  e8 0d 00 00                             法線 int16 x,y,z,0
```

- 頂点番号は `12, 8, 4, 0` → 4で割って `3, 2, 1, 0`
- 続く8バイトは `(549, -1949, 3560, 0)`。長さを測ると **4095.6 ≒ 4096**

4096 は 1.12 の固定小数の 1.0 なので、これは**単位法線**。
ダンプに出ていた4枚ぶんを全部測ったら 4095.6 / 4095.0 / 4095.4 / 4094.9 と
どれも 4096 だったので、読み違いではない。

    三角形 = 頂点番号 u32 ×3 ＋ 法線 8バイト = 20 バイト
    四角形 = 頂点番号 u32 ×4 ＋ 法線 8バイト = 24 バイト

この2つが混ざって並ぶ。本体の面の領域 12,736 バイトが 12 でも 24 でも
割り切れなかったのはこのため。1枚ずつ「法線がどこに来るか」で見分ける。

### もうひとつ分かったこと: 8つの部品はキャラクターではない

`+0x6F10` から並ぶ8部品は、この読み方では通らない。法線を持たず、
頂点番号3つ12バイトがずらりと並ぶだけ（どれもきっかり64枚）。
形も x が 3 から始まって左右対称の2組4本。**当たり判定か影のための形**で、
画面に出すものではないと判断した。

**キャラクターの見た目は `+0x0034` の部品ひとつ**（頂点854・法線470）だった。
v1.0.0 で「広がりが 199 → 724 に跳ねる」と書いたのは、
当たり判定と見た目を一緒くたに出していたせい。

この版でやったこと:

- 法線つきの面の読み方を実装（三角20バイト・四角24バイトの混在を1枚ずつ判定）
- ファイルに入っている法線をそのまま陰影に使う（面の裏表の取り違えがなくなる）
- 法線を持たない部品はふだん出さない。「当たり判定も出す」で切り替えられる
- 実物のバイト列をそのまま使った試験を5つ追加。

## v1.4.0 — 面のうしろの「おまけ」と、番号を共有する法線

v1.3.0 でも画面は変わらなかった（＝法線つきの読み方はまだ通っていない）。
報告を待つあいだに、すでに見えている数字から2つ直した。

### 1. 8部品の法線は、頂点と同じ番号で引く

8部品の色を見ると `ff c1 a3`（255,193,163）＝肌の色だった。
当たり判定ではなく、ちゃんと目に見える形だということ。
そして 8部品はどれも**頂点の数と法線の数が同じ**（51/51, 48/48, 47/47）。
本体だけが違う（854/470）。

    頂点の数 ＝ 法線の数 の部品 → 面は頂点番号3つだけ。法線は同じ番号で引く（なめらか）
    頂点の数 ≠ 法線の数 の部品 → 面のうしろに法線が1つ入っている（平ら）

PS1 のモデルでよくある2通りの持ち方そのままだった。
v1.3.0 までは 8部品の法線をまったく使わず、三角形の向きから計算していた。

### 2. 面のうしろに余分が付く形に対応

テクスチャの貼り方（UV や色パレットの位置）が面のうしろに付いていると、
1枚の長さが 24 バイトより長くなって読み方が途中で止まる。
1枚読むごとに、次の1枚がちゃんと始まる位置まで 4 バイト単位で読み飛ばし、
**読み飛ばした長さの内訳を報告に出す**ようにした。
ここに 8B や 12B がずらりと並べば、それがテクスチャのぶんということになる。

## v1.5.0 — 面は4種類あった

v1.4.0 の報告で、途切れた場所の前後がそのまま答えだった。

```
… 53 01 10 f0 6e 00 00 00 ┃ 0c 00 00 00 08 00 00 00 04 00 00 00 00 00 00 00 …
```

`┃` の左は法線 `(339, -4080, 110)`（長さ 4095.5 ＝ 4096）で終わっている。
右は `12, 8, 4, 0` → 4で割って `3, 2, 1, 0`、続けて `2, 5, 4, 1` `7, 6, 3…` と
**法線を持たない四角形**が並ぶ。辺を共有していく、いわゆる帯の並び方。

つまり面は4種類ある。PS1 のモデルでよくある、平らな面となめらかな面の組み合わせ。

| 種類 | 形 | 法線 | 1枚の長さ |
|---|---|---|---|
| A | 三角 | なし（頂点の法線を使う） | 12 バイト |
| B | 四角 | なし | 16 バイト |
| C | 三角 | あり | 20 バイト |
| D | 四角 | あり | 24 バイト |

本体 `+0x0034` は 70% が C/D、残り 30% が A/B だった。

### どこで切り替わるかは書かれていない

ファイルのどこにも「ここから法線なし」とは書かれていないので、読む側で決めるしかない。
しかも 12バイトの三角2枚と 16バイトの四角1枚は、どちらでもバイト数が埋まってしまう。

そこで2段構えにした。

1. **ぜんぶ同じ形で隙間なく並ぶか**をまず見る。腕や脚の8部品は 12バイトの三角64枚で
   768 バイトちょうど埋まるので、これで確定する。
2. 埋まらないとき（本体）は、**いちばん多くのバイトを説明できる並べ方**を
   後ろから決めていく。同点のときは「形として筋が通っているか」で選ぶ:
   - 同じ頂点が混ざっていないか
   - 四角なら4点が平らに乗っているか

## v1.8.0 — ゲーム本体のコードを読む（MIPS 逆アセンブラ）

エミュレータ（DuckStation）でメモリを見てもらったところ、2つ分かった。

**1. ゲームはポインタを書き換えていない。**
メモリ上のモデルも `面 0x24B8 / 頂点 0x5C0 / 法線 0x1FE8 / 色 0x61EC` と、
**ファイル内の相対位置のまま**だった。実アドレスに直していない。
つまりファイルの中身＝メモリの中身で、読み方の土台は合っている。

**2. `5, 1, X` の X は 0 とは限らない。**
別のキャラクターでは `5, 1, 46` で、`-4` の代わりに `-20` が出ていた。
どちらも4の倍数の負の数。命令の列らしさが強まった。

データはもう足りている。足りないのは**それをどう解釈するコード**のほう。
そしてそれは手元にある — 実行ファイル SLPS_004.00 はビューアがすでに読んでいる。

    ゲームは必ず署名 0x90000000 と比べる
      → コードに `lui ○○, 0x9000` が必ずある
      → バイト列で 00 90 ?? 3C
      → そこがモデルを読む関数

そこでビューアに **MIPS(R3000) の逆アセンブラ**を積んだ。

- `lui ??, 0x9000` を実行ファイル全体から探す
- 見つけた場所から前後へ、関数の切れ目（`addiu $sp,$sp,-N` ／ `jr $ra`）まで広げる
- その関数をまるごと逆アセンブルして報告に出す
- GTE（座標変換の専用回路）の命令も読める。頂点を触るところに必ず出てくるので、
  `RTPT` や `MVMVA` が見えればそこが変換の本体

これで「番号 0..167 をどうやって 854個の頂点に届かせているか」が、
推測ではなくコードで確かめられる。

## v1.9.0 — ファイルの頭の形が、コードで確定した

v1.8.0 の逆アセンブラが `0x80068080` の関数を当てた。これがモデルのファイルを開く本体。
読み解くと、ファイルの頭はこうなっている（**推測ではなくコードそのもの**）:

```
lw   $s0, 2796($s2)      ptr = ファイルの先頭
lw   $v1, 0($s0)         署名を読む
bne  $v1, $v0, 抜ける    0x90000000 でなければ終わり
addu $s4, $s0, $zero     base = ファイルの先頭          ★控える
addiu $s0, $s0, 4
lw   $a0, 0($s0)         offset0 を読む
addu $a0, $s4, $a0       base + offset0                 ★足す
jal  0x8001BE24          ← 部品を読む関数へ
...
lhu  $v0, 0($s0)         個数（16ビット）
loop:
  lw   $a0, 0($s0)       部品の位置
  addu $a0, $s4, $a0     base + 位置                    ★また足す
  jal  0x8001BE24
```

分かったこと:

- **位置はすべてファイルの先頭からの相対**。`base + 位置` で実アドレスになる。
  ビューアの読み方と一致していた
- **個数は `lhu`（16ビット）で読んでいる**。32ビットだと思っていたが、
  上位16ビットは別の意味かもしれない
- 部品の列は**3組**ある（#68 は 4個 / 4個 / 0個）。
  「0 で終わり」だと思っていたのは「3組目が0個」だった
- **部品を読む本体は `0x8001BE24`**。頂点の番号をどう扱うかはこの関数の中

この版では、見つけた関数が `jal` で呼んでいる先も自動で辿って逆アセンブルする。
`jal` の飛び先が負の数で出ていた不具合（符号なしにし忘れ）も直した。

## v2.0.0 — 1,504バイトの正体は「命令の列」だった

呼び出し先 `0x8001EEE4` が全部教えてくれた。

```
lw $s2, 0($fp)        面の位置
lw $a0, 4($fp)        頂点の位置
lw $s3, 8($fp)        法線の位置
lw $s4, 12($fp)       色の位置
addiu $fp, $fp, 16    ← ヘッダは16バイトだけ。この先は命令の列

ループ:
  lw $v1, 0($fp)      命令コード
  lw $s6, 4($fp)      引数
  lh $t1, 1014($s0)   いまの「ベース」（16ビット、スクラッチパッド 0x1F8003F6）
  addu $t1, $s6, $t1  ベース ＋ 引数
  addiu $fp, $fp, 8   命令は8バイト
  jr $v1
  sh $t1, 1014($s0)   ★ ベース = ベース + 引数（累積）
```

**部品のヘッダは4つの位置（16バイト）だけ**で、そのあとは
**8バイトずつの「命令コード＋引数」の列**だった。

そして `0x1F8003F6`（スクラッチパッド）に**16ビットの「ベース」**を持ち、
命令のたびに引数を足し込んでいる。**これが 854対167 の答え**。
頂点番号は部品の通し番号ではなく、**このベースからの相対**だった。
「小部品ごとに振り直し」という見立ては当たっていたが、区切りの幅は
面から推測するものではなく、**命令列に書いてあった**。

裏も取れた。腕の部品 `+0x6F10` を命令として読むと:

| 位置 | 中身 | 意味 |
|---|---|---|
| +0x10 | `(5, 2)` | 命令5、引数2 |
| +0x18〜+0x30 | `0, 51, 51, 10, 20, 11, 33` | 命令5が読むデータ（頂点51・法線51・面の数） |
| +0x34 | `0` | **命令0 ＝ 終了** |

v1.0.0 から「部品は 0 で終わる」と書いてきたが、正体は**終了命令**だった。

命令の振り分けも読めた:

    命令 1 → 0x8001F1B0    命令 2 → 0x8001F264    命令 3 → 0x8001F428
    命令 4 → 0x800205DC    命令 5 → 0x8001F44C    命令 6 → 0x8001F434
    命令 7 → 0x8001F1E0    命令 8以上 → 飛び先の表（0x80021FCC など）

この版では、逆アセンブラが**分岐の飛び先**と**飛び先の表**も自動で読むようにした。
命令ごとに何をするか（どれだけデータを食うか、ベースをどう動かすか）が分かれば、
モデルの読み方はそのままコードに書き写せる。

## v2.1.0 — 「頂点番号 ×4」の正体が分かった

命令1の処理（`0x8001F1B0`）が決定打だった。

```
sll  $v0, $s6, 1        v0 = 引数 × 2
lw   $a3, 8($fp)        3つ目の語を読む（命令1は8バイトではなく12バイト）
lw   $a0, 1016($s0)     頂点ポインタ（スクラッチパッド 0x1F8003F8）
sll  $t0, $a3, 3        3つ目の語 × 8   ← 頂点は8バイト
addu $t0, $a0, $t0
sw   $t0, 1016($s0)     ★ 頂点ポインタを「その個数ぶん」進める
subu $a2, $s1, $v0
sll  $v0, $v0, 1        引数 × 4
jal  0x8001F024         ← RTPT（座標変換）へ
addu $a1, $s0, $v0      ★ 置き場所 = 0x1F800000 + 引数×4
j    ループへ
addiu $fp, $fp, 12      命令1は 12 バイト
```

つまり命令1は **「頂点を N 個読んで座標変換し、スロット番号 M から順に置く」**。

    命令1 = (1, 置き場所M, 個数N)   12バイト
      → 頂点ポインタから N 個読む（頂点ポインタは N×8 進む）
      → 変換した結果を スクラッチパッドの M×4 の位置から順に置く

そして **面の「頂点番号 ×4」は、このスロットの位置そのもの**だった。
スクラッチパッドは 1KB（0x1F800000〜0x1F8003FF）しかないので、
**スロットは最大でも 250個ほど**。実測で番号の最大が 167 だったのは当然だった。

頂点854個に対して番号が 0..167 なのは「振り直し」ですらなく、
**頂点はいったん小さな置き場所に移され、面はその置き場所を指している**という仕組み。
命令列を頭から実行して「どのスロットに何番の頂点が入っているか」を追えば、
面が本当はどの頂点を指しているかが分かる。

この版では、**命令ごとの「1つの長さ」をコードから自動で割り出す**ようにした。
どの処理も最後は `j ループの先頭` に戻り、その遅延スロットで `addiu $fp, $fp, N`
と進めている。その N を全命令ぶん拾って一覧にする。
あわせて「頂点ポインタを動かすか」「何語目まで読むか」「座標変換するか」も出す。
これが揃えば、あとは同じ手順をなぞるだけでモデルが組める。

## v3.3.0 — 切り分けの道具（本体だけ／骨ごとに色分け）

[ 7] 14枚  範囲 x -70..395  y -125..37   z -41..43     同じ

```

**X方向に長い細い部品**が並んでいる。腕や脚の形そのもの。

さらに左右対称のペアがきれいに出ている:

## v3.7.0 — 8個の部品の正体は「手」だった

「部品を並べる」で横に離して見たら、はっきり分かった。

### 命令 3/5/6 が読めた

実行ファイルの中身を見たら、3つとも数命令の短いものだった。

```

命令6 (8B)  旗が立っていなければ $s7 += 引数
命令5 (4B)  0x800CBE90 / 0x800CBE8C にある「表」から次の1件を取り出す

命令5 がいちばん大事で、こうなっている:

```

t0 += 4 ; t1 += 4         1件ぶん進めて
*(0x800CBE90) = t0        進めた位置を書き戻す
t5 = 前の t0 の中身        取り出した1件は「行列を指すポインタ」

これで間違いない。

## v3.9.0 — 骨さがし

命令5 が引く表は「行列を指すポインタの並び」だった。その行列はプレステの MATRIX で、
**ちょうど32バイト**:

```
int16 m[9]   回転（1.3.12 の固定小数。1.0 が 4096）  18 B
詰め物                                                2 B
int32 t[3]   移動量                                   12 B
                                                 計 32 B
```

キャラクターのモデル（sector 5927）のすぐ後ろ、sector 6016〜6312 のファイルには
**928 バイトの塊**が何十個も並んでいる。そして

```
928 ÷ 32 = 29  ← ちょうど割り切れる
```

本体の命令5 の区切りが26個、それに手が左右で2個、根っこが1個で 29。数が合う。

### 見分け方

でたらめなバイト列を行列と読み違えないように、**回転行列であることを確かめる**:

- 3本の行の長さがどれも 4096（±12%）
- 3本が互いに直角（内積が 0.12 未満）

この2つを同時に満たすバイト列は、でたらめでは出てこない。試験でも、
本物と同じ作りで作った29個は全部通り、でたらめな並びは1個も通らなかった。

### 使い方

左の欄の**「骨さがし（32バイトの行列を探す）」**を押すと、アーカイブの中の
183ファイルを全部あたって、32バイトの行列が並んでいる塊を探す。
見つかったものは解析結果に、回転と移動量の中身つきで出る。

## v3.12.0 — モデルを描く関数が読めた

0x80068080 が読めて、ファイルの読み方がコードから裏づけられた。

```

count1 = 半語 *(s0)       ※半語で読むが、位置は4バイト進む
*(s2+0xAE4) = count1
count1回:
  a0 = s4 + *(s0)         組1の部品
  *(s3+0xB40) = a0        ← 覚えておく場所。4バイトずつ

### 分かったこと3つ

**2. 組は「4個まで」と決まっている。** 覚えておく場所が 0xB40 / 0xB50 / 0xB60 と
16バイト刻み＝ポインタ4つぶん。組の大きさが4なのは偶然ではなかった。

**3. ゲームは組の部品を全部描いている。** ループの中で毎回 0x8001BE24 を呼んでいる。
つまり「組から1つだけ」というこの版の見せ方は、**ゲームの動きとは違う**。
ただし置き場所（行列）が分からないうちは全部が原点に重なって棘になるだけなので、
表示の都合としてはこのままにしておく。

### 0x800CBE88 / 8C / 90 は3つ並んだ構造体

0x8001BE24 は描く前に 0x800CBE88 に 1 を、終わったら 0 を書く。
