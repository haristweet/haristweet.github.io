# cd-ripcheck

大量にリッピングしたCDを、**聴かずに**検査する道具。

音飛びしたまま気づかずライブラリに積まれていくのを防ぐ。
1枚50分かけて聴くかわりに、疑わしい箇所の前後3秒だけを聴く。

---

## 考えかた

**聴いて確認するのは現実的でない。** 500枚なら約420時間かかるうえ、
人間の耳は数十msの飛びをふつうに聞き逃す。機械のほうが確実で速い。

対策は3段構えになる。上から順に費用対効果が高い。

| 段 | やること | 費用 | 人間の手間 | 効き |
|---|---|---|---|---|
| **1. 予防** | XLD でリップし、AccurateRip と照合する | 0円 | 0秒 | ◎ ここで大半が片づく |
| **2. 事後検査** | このツールでライブラリ全体を走査 | 0円 | 疑わしい箇所だけ試聴 | ○ DBに無い盤を拾う |
| **3. 運用** | launchd で自動化し、Claude Code で調整 | 0円 | 週1でレポートを見る | ○ 続けられる形にする |

**このリポジトリは 2 と 3 を担当する。** 1 は XLD の設定だけなので、
後述の「XLD の設定」を先にやってほしい。そちらのほうが効く。

---

## 何を検出するか

合成した欠陥入り音源での実測値。正常な音源で誤検出 0 件を確認している。

| 種類 | 中身 | 検証結果 |
|---|---|---|
| `flac_md5_mismatch` | FLAC 内蔵の MD5 と中身が食い違う | 破損ファイルを検出 |
| `decode_error` | そもそもデコードできない | 検出 |
| `energy_drop` | **主力。**一瞬だけ音量が落ちて戻る | 実際に音飛びのある実ファイル（5分半）で **110箇所**を検出。正常音源・320k/128k の mp3 で誤検出 0 件 |
| `digital_silence` | 曲の途中の完全無音（全ビット0） | 13.3ms（CD 1セクタ）から検出。**可逆圧縮のときだけ有効** |
| `lossy_suspect` | 高域が断崖状に切れている | 正常 0.8dB に対し mp3 由来 63〜66dB（閾値 25dB） |
| `too_short` | 数秒しかない。リップの残骸 | 検出 |
| `discontinuity` | 波形の不連続 | **既定で無効。**実音楽では機能しない（後述） |

`energy_drop` が主力で、`digital_silence` はその特殊ケース（可逆圧縮で欠落が
完全な0のまま残っている場合）という関係になっている。AAC や mp3 を経由すると
欠落は微小ノイズに化けて 0 ではなくなるので、周囲との比で見る必要がある。

### 時間分解能が決定的

実ファイルの音飛びは **長さの中央値が 2ms** しかない。10ms 刻みで見ると
平均に埋もれ、110 箇所のうち 1 箇所しか見つからなかった。`drop_hop_ms` を
2.0 にすると全部見つかり、誤検出は 0 件のまま。**この値を大きくしないこと。**

同じ理由で `drop_guard_sec`（曲頭を無視する秒数）は 0.25 にしてある。
2.0 にすると曲の出だしの音飛びを隠してしまう。周囲が鳴っていることは
`drop_context_level` で確かめているので、長いガードは要らない。

`lossy_suspect` は音飛びとは別問題だが、**一括検査でいちばん収穫があるのはここ**かもしれない。
「FLAC だと思っていたら mp3 から作られていた」は耳ではまず気づけない。

## 使いかた

```bash
git clone <このリポジトリ> ~/claude/cd-ripcheck
cd ~/claude/cd-ripcheck

# まるごと検査（初回）
MUSIC_ROOT=~/Music ./scan.sh

# 以後は差分だけ。毎晩流しても数秒で終わる
MUSIC_ROOT=~/Music ./scan.sh
```

`work/` に結果が出る。

| ファイル | 中身 |
|---|---|
| `work/report.md` | **これを読む。** 怪しい順のアルバム一覧と内訳 |
| `work/suspect/*.wav` | 疑わしい箇所の前後3秒。**ここだけ聴けばいい** |
| `work/report.jsonl` | 検出の生データ（1行1件）。集計や再解析用 |
| `work/xld.jsonl` | XLD ログから抽出した AccurateRip 判定 |
| `work/flac_test.log` | `flac -t` で落ちたファイルのパス |

`MUSIC_ROOT` は毎回書くのが面倒なら `config.sh` に置く（gitignore 済み）。

```bash
echo 'MUSIC_ROOT=~/Music' > config.sh
```

### 個別に動かす

```bash
./scan_library.py ~/Music --jobs 8 --out report.jsonl   # 波形検査だけ
./parse_xld_log.py ~/Music --out xld.jsonl              # XLDログだけ
./triage.py --report report.jsonl --clips suspect/      # 集計と切り出しだけ
```

主なオプション:

- `--rescan` — キャッシュを無視して全部やり直す（閾値を変えた後に使う）
- `--min-age 300` — 直近5分に更新されたファイルは見送る（リップ中の書きかけ対策）
- `--jobs N` — 並列数
- `--thresholds thresholds.json` — 閾値ファイル

途中で Ctrl-C しても、次回は続きから走る。

## 所要時間

1コアあたり **実時間の 90〜125 倍速**（実測）。ただし実際にはディスク I/O が
律速になることが多い。

| ライブラリ | 音声の総時間 | 8コアでの目安 | 読み込み量 |
|---|---|---|---|
| 100枚 | 約 80時間 | 5〜10分 | 約 35GB |
| 500枚 | 約 420時間 | **30〜60分** | 約 175GB |
| 2000枚 | 約 1,700時間 | 2〜3時間 | 約 700GB |

NAS 越しだとネットワークが上限を決めるので、**ローカルディスクのほうが速い**。
2回目以降はキャッシュが効くので、増えたぶんだけ。

## 誤検出との付き合いかた

**一括で回すと必ず大量に引っかかる。** これは前提。とくに：

- テクノ / グリッチ / ノイズ系 — 意図的なクリックの塊
- ライブ盤・古い音源 — もともとプチノイズがある
- アナログ盤起こし — 全編スクラッチノイズ

**閾値を下げて全体を鈍らせるのは最後の手段。** 先に `exclude.txt` で
効かない対象を名指しで外すほうが、副作用が小さい。

```
# exclude.txt — パスの一部一致か glob
/Users/you/Music/Autechre
*/Vinyl Rip/*
*/Bandcamp/*
```

そのうえで `work/report.md` を**上から順に**見て、`work/suspect/` の
切り出しを聴く。1本3秒なので50件でも3分で終わる。

閾値そのものを触るときは `thresholds.json`。変更後は `--rescan` が必要。

## XLD の設定（こちらのほうが重要）

**AccurateRip で一致が取れたトラックは、ビットパーフェクトがほぼ確定する。
そもそも聴く必要がない。** 世界中の他人が同じ盤をリップした結果の CRC と
照合する仕組みなので、1サンプルの狂いも見逃さない。

XLD の環境設定でこうする。

- Ripper Mode → **XLD Secure Ripper**
- **Test & Copy を有効**（2回読んで CRC を比較する）
- **AccurateRip を有効**、あわせて **CUETools DB (CTDB)** も有効
- **ログを音源と同じフォルダに保存**（`parse_xld_log.py` がこれを読む）

これでリップ1枚あたりの追加時間はおよそ倍（10〜15分）、人間の手間はゼロ。

ログがあると `report.md` に「何トラックが AccurateRip 一致＝聴かなくてよい」
まで出るので、検査対象がはっきり絞れる。

## 自動化（launchd）

`launchd/com.ripcheck.scan.plist` を `~/Library/LaunchAgents/` に置いて、
`/PATH/TO` と `/Users/YOU` を書き換えてから：

```bash
launchctl load ~/Library/LaunchAgents/com.ripcheck.scan.plist
```

- リップ先フォルダが増えたら自動で走る（`WatchPaths`）
- 毎晩3時にも走って取りこぼしを回収する（`StartCalendarInterval`）
- `Nice` と `LowPriorityIO` を設定してあるので、他の作業を邪魔しない

`WatchPaths` は XLD がフォルダを作った瞬間にも発火してしまうので、
`scan.sh` 側で「直近5分に更新されたものは見送り」にしてある。
見送られたファイルは次回か深夜の定期実行で拾われる。

## 既知の限界

正直に書いておく。

- **`discontinuity` は既定で無効。実音楽では機能しない。** 合成音源では分離
  できたが、実際の AAC ファイル1本（5分半）で誤検出 1184 件を出し、しかも
  同じファイルに実在した本物の音飛びのスコアは 12 で閾値 25 にすら届かなかった。
  非可逆圧縮を経由すると欠落の縁が鈍らされること、低音の密度が高い曲では
  波形構造そのものが大きな2階差分を生むことが原因。振幅比・局所中央値・
  立ち上がり比のどれを併用しても分離できなかった。音の薄いアコースティック
  録音などでは効く可能性があるので、`thresholds.json` の `disc_enabled` で
  有効にできるようにしてある。
- **高ビットレートの AAC は `lossy_suspect` で検出できない。** 高域を切らない
  エンコーダがあるため。mp3 は確実に引っかかる。
- **モノラルに畳んで解析している。** 片チャンネルだけの欠落は鈍る。CD の
  読み取り失敗は両チャンネルに同時に出るので実用上は困らない。
- **「元から音飛びして記録されている」ものは `flac -t` では見つからない。**
  正しく音飛びを保存しているため。だから波形検査が要る。
- **AccurateRip に載っていない盤**（自主制作・同人・マイナーな邦盤）は
  照合できない。波形検査だけが頼りになる。

既に大量にリップ済みのライブラリに対しては、**CUETools（Windows）で CTDB と
照合するのが最強**。一致しないトラックを DB から修復までできる。
Mac では Parallels / CrossOver / Wine が要るのが難点。

## ファイル構成

```
ripcheck.py        検出ロジック本体。閾値はすべて Config にある
scan_library.py    フォルダの一括走査。キャッシュ・並列・中断復帰
parse_xld_log.py   XLD ログ → AccurateRip 判定の JSONL
triage.py          集計してレポート化。疑わしい箇所を切り出す
scan.sh            上を順に回す。launchd から叩かれるのもこれ
thresholds.json    閾値
exclude.txt        検査から外すパターン
launchd/           自動実行の plist
CLAUDE.md          Claude Code 向けの手引き
```
